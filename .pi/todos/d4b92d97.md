## Bug 1: Race condition in `handleSharedServerStarted` / `handleDirectoryChanged`

These methods set `this.listenerLoopRunning = false` and call `void this.startEventListener()`. But the OLD `startEventListener` loop may still be running. The `listenerAborted` getter reads from `this.state?.listenerController`, which was updated to a new (non-aborted) controller. So the old loop's `while (!this.listenerAborted)` check returns `false` → old loop doesn't exit → TWO loops run simultaneously, both logging "Connected to event stream".

**Fix**: Capture the `AbortSignal` at the start of each loop iteration (already done via `const signal`), but also check if the signal that was captured has been aborted, even if the state has been replaced. The simplest fix is: instead of relying on `listenerAborted` which reads from mutable state, capture the signal at loop start and use `signal.aborted` directly in the while condition.

## Bug 2: No backoff when SSE stream ends normally

When the `for await (const event of events)` loop completes without error (stream closed cleanly), the code doesn't add any delay before the next iteration of the `while` loop. This creates a tight reconnect loop, especially if the server keeps closing the connection.

**Fix**: Add a delay at the bottom of the while loop for the non-error case (stream ended cleanly).

## Bug 3: `startEventListener` reentrancy guard is insufficient

The `listenerLoopRunning` flag is set to `false` by `handleSharedServerStarted`/`handleDirectoryChanged` before calling `void this.startEventListener()`. But the old loop also checks this flag. The old loop already has `listenerLoopRunning = true`, so the flag set to `false` by the handler means the new `startEventListener()` call won't be blocked. However, the old loop doesn't re-read this flag - it just keeps running.

**Fix**: Have the while loop capture its own signal at the start and check `signal.aborted` directly, not the live `listenerAborted` getter.
